# Build progress and handoff

Last updated: 7 Nov 2026, release 1.0.6: a test update (no app changes) for the live pop-up test at the shops.
This file is for whoever continues the work: a person or a new Claude session. The spec is `docs/POS_System_Plan.pdf`; section names below match the plan's headings.

## State in one paragraph

Phase 1 ("go-live core") is mostly built and tested end to end. The shared rules, data model, server API, and screens for Billing, Stock and Admin all work against a real PostgreSQL database. The Windows installer and automatic updates are built (see Foundation). What Phase 1 still lacks: data import from the old system, Sinhala receipts, and the restore wizard. Two-way cloud sync and the online panel are built (see Foundation). The rest of Phase 2 (reports, closing, reorder) and Phase 3 have not started, but the database tables for most of them already exist.

Test status on 6 Nov 2026: `pnpm typecheck` is clean; 89 shared unit tests, 124 server integration tests (`test/sync.test.ts` runs a shop app and a cloud app side by side) and 11 Playwright keyboard e2e tests all pass. The tests follow the owner's later changes on `main` (see "Owner's changes the tests now follow" below).

### Foundation
- ✅ Login with username + password; PIN user switching; idle screen lock (client timer + server enforcement); forced password change after reset; 8 printed recovery codes for the Super Admin.
- ✅ Roles by checkbox (combined per user), custom roles built from module permissions, safety rules (an active Super Admin always remains; Super Admin-only permissions can't go into a custom role), and server-side permission checks on every route.
- ✅ Per-permission control. The Super Admin opens a role to see its permissions:
  - Built-in roles (not the Super Admin) can be changed for everyone who has them (`roles.customized`) and put back with "Back to default" (`POST /api/roles/:id/reset`).
  - Each user can also get extra permissions, or lose some, on top of their roles (`user_permissions`, sent as `permissionOverrides`).
  - The rule lives in `shared/domain/permissions.ts` (`rolePermissions`, `resolvePermissions`), and the screen is `admin/PermissionEditor.tsx`.
- ✅ Manager override by PIN, with both names in the audit log (void, mix price change, open can, write-off, old-system return, reverse purchase).
- ✅ Per-user shortcut keys: remap in My profile, validation against reserved and already-used keys, reset to default, F1 help, Ctrl+K command palette.
- ✅ Value manager: categories, brands, units (with an allows-decimal flag), locations (Super Admin only), reasons (with "applies to"), cutoff types. Unique names ignoring case and spaces, merge with history, deactivate when in use, ordering. Missing values are added from the picker itself (see "Pickers" under Look and feel).
- ✅ Audit log: written in the same transaction as each change; append-only at the database level; viewer with filters and before/after values.
- ✅ Sync outbox written from day one by DB triggers in the same transaction; each change also carries the row before it (`sync_outbox.old`), captured in UTC.
- ✅ **Two-way cloud sync and the online panel, for several shops** (`core/syncagent.ts`, `core/syncapply.ts`, `core/shops.ts`, `modules/sync/`, Admin → Cloud sync):
  - **Each shop works fully offline.** The same app runs in the cloud with `APP_MODE=cloud`, its own PostgreSQL and `SYNC_KEY`. Each shop server's agent (every 15 s) sends its outbox to `POST /api/sync/push`. The first time a shop connects, the cloud makes that shop's own copy database (`<cloud db>_s_<id>`, built from the migration files) and lists it in its own `sync_nodes`. Changes are applied once each, in order, without capturing them again (`aruna.sync_apply`); a row that can't be applied is skipped and noted.
  - **Who opens it:** the permission "Open the online panel" (`cloud.access`, Permission editor → Online panel). Admins and the Super Admin have it by default, and the Super Admin can give it to anyone. On the sign-in page you choose the shop, then use your username and password at that shop. Each shop's sign-in is kept, so switching shops (top bar or Cloud sync → Shops) needs a sign-in only the first time.
  - **Everyone else only looks:** the shop's stock, bills, dashboard and so on, as of its last sync ("Data as of …" in the top bar). Online, their permissions are cut to viewing (`onlinePermissions`), so edit buttons don't show, and the server refuses any write ("The online panel is view-only. Changes are made at the shop."). The billing screen and day end are hidden online.
  - **The Super Admin changes only what an Admin can't:** users, passwords, PINs, roles and permissions, test mode, the settings and colour theme (backup times and folders too; not the shop's cloud link, which could cut it off), number formats, the receipt printer, the HRM month start and each month's figures (`ONLINE_CHANGES` in `modules/sync/online.ts`). Online the Super Admin keeps every Super Admin-only permission (`onlinePermissions`). Things only the shop's server can do, "Back up now" and "Refresh test copy", are asked for online (`SHOP_REQUESTS`): the shop does them at its next sync, in that Super Admin's name, and Cloud sync shows how it went. Each change shows online at once, is kept as the rows it changed (`sync_commands`), and is applied at that shop when it next connects. Billing, stock, products, suppliers and payments are refused online: "This can only be done at the shop."
  - **Conflicts, field by field:** an online change is applied when the shop didn't change the same fields meanwhile; different fields changed at each end are both kept. When the shop changed the same field (a settings group counts as one field), it waits as a **conflict**: the Super Admin chooses "Use online change" or "Keep shop version", online or at the shop. A change the shop can't take (a PIN or username already used there) is "Not applied", and the cloud shows the shop's rows again.
  - **Shops and last sync:** the Super Admin's Cloud sync page lists every shop: online or offline, last sync, today's bills and sales, changes waiting, the last bill, version. Others see their own shop. At the shop the page shows online/offline, last sync, what is waiting, the last error and "Sync now".
  - **The owner: the one top Super Admin, at every shop** (`modules/sync/owner.ts`, `users.owner`; the owner's request). The first Super Admin who signs in on the online panel with their usual username and password becomes the owner (kept in the cloud's `sync_state` key `owners`); later Super Admins don't. The owner's one sign-in (a signed `aruna_owner` cookie) opens every shop, new ones included (`ownerSession`). Their account is at every shop as a Super Admin marked owner (`provisionOwner`, sent like an online change, labelled "Owner account added/updated"), so the same username and password work at every shop's PCs; someone else with that username at a shop is never taken over. A password changed online, at any shop (seen in its push, `ownerAfterPush`) or used at the latest online sign-in reaches every shop; PINs stay each shop's own, except one set online. **Only the owner** sees every shop on Cloud sync, removes shops, and changes the owner's account (`guardOwner` in `users/service.ts`, at the shop and online; the Users page shows "Owner"). Other Super Admins belong to the shops they are added to (the owner adds them there). **A new shop needs no account:** the first-run wizard links it to the online panel (address and shop key) and makes no user; the login page waits ("waitingForOwner") until the owner's account arrives with the first syncs. Setting up without the online panel (its own Super Admin) stays for a shop with no internet.
  - **A full copy of the shop when the cloud has none** (`sync_full_copy()` in migration `20261104110000_sync_full_copy`, `fullCopyIfNeeded` in the agent, `emptyCopy` in `sync/cloud.ts`). The shop queues every synced row, parents before children and shaped like the captured rows, after a `__full_copy__` marker that makes the cloud empty its copy first; unsent changes are replaced by it under a lock on the outbox. It happens when the shop has no `full_copy` note (the first link, after the update, after `db:clean`) or when the cloud answers `needFullCopy` (its copy never had one: `sync_nodes.full_copy_at`). Before this, a shop linked after its users and roles were made, or one whose outbox was cleared, reached the cloud without its roles ("You are not allowed to open the online panel"). The cloud retries rows whose parent comes later in the batch.
  - **Removing a shop from the panel** (Cloud sync → Shops, Super Admin, `DELETE /api/cloud/shops/:id`): its copy is dropped; if its server connects again it comes back as a new shop with a full copy. Shops with the same name show when each was last seen on the sign-in page.
  - **`db:clean` keeps the shop's id at the cloud** (it used to empty `sync_state`, so the shop turned up as a second shop) and the next sync replaces the cloud's copy with the cleaned data.
  - **Nothing on the online panel is cached in memory** (`SettingsService` with `keep = false`; the default location is looked up each time): shops' syncs change the rows behind it, and on Vercel several copies of the server answer at once. Before this, a colour theme changed at the shop never showed online.
  - **Hosting: Vercel with Neon PostgreSQL** (step by step in `docs/CLOUD_ON_VERCEL.md`). `vercel.json` runs `apps/server/scripts/vercel-build.mjs`, which writes `.vercel/output` (Build Output API). That holds the screens as static files and the server bundled into one function (`src/vercel.ts`, with Prisma and the migrations), and the script runs the migrations on the cloud's database. Neon's `DATABASE_URL_UNPOOLED` (or `DIRECT_DATABASE_URL`) is used for making shop databases and migrations. Each shop's copy takes new migrations when it is next opened (`bringUpToDate` in `core/migrations.ts`, which test-mode copies use too). Online, the screens refresh on a timer (no WebSocket on Vercel). The bundle was run locally as the cloud with a shop syncing to it; the Vercel deploy itself still needs the owner's account.
- 🟡 Backups: `pg_dump` at day end and nightly (`backup.nightlyAt`), keeping 30 daily and 12 monthly copies, optional second folder, failure alerts, manual backup API, backup list. **Missing:** a cloud copy, the restore wizard, the monthly test-restore reminder, and a UI to start a backup.
- ✅ **Windows installer** (`installer/`, steps for the shop in `docs/SHOP_SERVER.md`): one `ArunaPOS-Setup-<version>.exe` for a clean 64-bit Windows 10/11 PC; the person clicks Next, Install and waits.
  - `installer/build.mjs` (Linux or Windows, needs `makensis`) stages Node.js for Windows, PostgreSQL 16 (EDB binaries without pgAdmin), the Visual C++ runtime, WinSW, the server bundled by esbuild into `app/server.mjs` and `app/migrate.mjs` (version baked in as `ARUNA_BUILD_VERSION`), Prisma's client with its Windows engine (`binaryTargets = ["native", "windows"]`), the migrations and the screens (`app/web`), then compiles `installer/windows/aruna.nsi` and writes `dist/latest.json` with the SHA-256.
  - `tools/setup.ps1` does the work on the PC. **First install:** `C:\Program Files\Aruna POS` for the program, `C:\ProgramData\ArunaPOS` for data (Administrators and SYSTEM only), random database passwords and PIN secret in `config.env`, a PostgreSQL cluster on port 5544 listening on localhost only as service `ArunaPOS-DB` (NetworkService), the empty shop database with every migration, the server as service `ArunaPOS-Server` (restarts itself), a firewall rule for port 3000 from the local subnet, the `Aruna POS Updater` task, and desktop/Start menu icons that open Edge in an app window. **The database starts empty**: the first-run wizard links the online panel (the owner arrives by sync) or makes the owner's account; no demo data, no other users. **Run again** it updates (below). **Uninstall** removes services, task and firewall rule and keeps the data unless the person says otherwise; installing again brings it back.
  - **The PIN secret follows the online panel:** the cloud sends its `PIN_SECRET` with the online changes (`GET /api/sync/commands`, shop key only), and a shop takes it while no user there has a PIN (a new shop, before the owner's account arrives), keeps it in `sync_state` key `pin_secret` (never synced) and uses it from then on, restarts included (`usePanelPinSecret` in `app.ts`). So PINs set online, the owner's included, work at every new shop. A shop that already has PINs keeps its own secret (switching would break every PIN there); `SyncStatus.pinSecretShared` is then false and Cloud sync says so. `/PINSECRET=` on the installer sets it up front; `/S` is silent.
  - **Migrations without the Prisma CLI:** `src/scripts/migrate.ts` → `migrateShop()` in `core/migrations.ts` applies the migration files in Prisma's own `_prisma_migrations` table with Prisma's checksums, so it and `prisma migrate deploy` agree (tested: identical schema). `--create` makes the role (with CREATEDB for test mode) and database first.
  - **CI:** `.github/workflows/installer.yml` builds it on Ubuntu, then on a clean `windows-latest` machine installs it silently and tests the health check, the empty first-run state, setup leaving one user, an update over it (backup made, data kept), the updater task, uninstall (data kept) and reinstall over the kept data. A `v*` tag publishes the release only after all of that passes.
- ✅ **Automatic updates** (`core/updates.ts`, Settings → Software updates for the Super Admin at the shop; `GET /api/updates`, `POST /api/updates/check`, `POST /api/updates/install`):
  - The installed server checks `https://api.github.com/repos/KING-UPE/Aruna_Paint/releases/latest` every 15 minutes and at start, with the ETag so unchanged answers (304) cost nothing against GitHub's 60-an-hour limit (repository: `UPDATE_REPO`), reads `latest.json`, downloads a newer installer to `data\updates` and keeps it only if its SHA-256 matches.
  - It installs at `updates.installAt` (02:30 by default, setting group `updates`) when `updates.auto` is on, or when the Super Admin presses Install: it checks the file again, writes `pending.json` and starts the `Aruna POS Updater` task, which runs as SYSTEM outside the server's service, checks the hash once more and runs the installer silently.
  - The installer backs the database up (`before-update-<from>-to-<to>-<time>.dump`), stops the server, swaps the program (PostgreSQL only within the same major version), migrates, starts the server and waits for `/api/health` to answer with the new version. On any failure it puts the previous program and the backed-up database back and starts the old version. Its `last-result.json` becomes `update.installed` / `update.failed` in the audit log (and an alert when it failed) at the next start.
  - **"Update ready" pop-up (1.0.4):** as soon as a version has downloaded, the Super Admin and Admins (not cashiers) get a pop-up on whatever screen they are on (`layout/UpdatePrompt.tsx`, from `update` in `GET /api/system/status` and the live event `update`): **Tonight at <installAt>** (focused, so a stray Enter never starts an install), **Next time the shop opens** (the first check after the server restarts installs it, once: `installIfChosenAtStart`), **Install now**, or **Remind me later** (asks again in 2 hours, per browser). The choice is kept in `data\updates\choice.json`, logged as `update.scheduled`, and shown in the status bar ("Update 1.0.5 installs at 02:30"), which reopens the pop-up. "Tonight" installs at the set time even when automatic installs are off. Admins may now check, choose and install updates too (`updateManager` in `modules/system/routes.ts`).
  - **Update tests before every release (1.0.5):** the workflow's `build-update-tests` job builds 0.9.x variants of the same app (`TEST_VARIANT` in `installer/build.mjs`: a good migration, a migration that makes a table and then fails, a server that exits at start), and `test-updates-on-windows` installs 0.9.0 with data on a clean Windows runner, then updates to each: data kept and the change applied; the failing change (started through the updater task) rolled back with the half-made table gone and the data back; the dead server rolled back; both failures shown as `UPDATE_FAILED` alerts; and a normal update to the real build afterwards with no `.prev` folders left. `release` needs it. It found that no update result was ever reported: Windows PowerShell 5.1 writes UTF-8 with a byte-order mark, which `JSON.parse` refused (fixed in 1.0.5 on both sides).
  - Release notes for the pop-up's "What is new" come from `docs/releases/<version>.md`.
  - Only a server put in by the installer installs (`ARUNA_INSTALL_DIR`); elsewhere the card says so. A source install still updates with `pnpm shop:update` (`apps/server/scripts/update-shop.mjs`).

## Decisions taken where the plan was silent or ambiguous

These were my calls; confirm them with the owner if any matters:

1. **Number format tokens** use braces (`INV-{NNNNNN}`, `GRN-{YYYY}-{NNNNN}`, `DE-{YYYY}{MM}{DD}`, plus `{YY}` and `{LOC}`). Without braces, the N in "INV" would be read as a digit. A format with a date counts per date scope (GRN restarts every year).
2. **The invoice number is taken at payment, not when the bill starts.** The top bar shows a preview of the next number. Held bills have no number, so numbers stay gap-free.
3. **A mix paint price changed at the counter applies to that line only** (Admin PIN, logged on the line). The stored price per liter changes only through a mix-paint transfer.
4. **Converting a quotation keeps the quoted net price until the validity date**, even above the counter discount cap. A lower current price wins, and it never sells below cost; if it would, the cashier is told to quote again. Batches are re-picked oldest first.
5. **Admins don't create GRNs**, because the GRN screen shows cost and Admins must not see cost. They can view purchases (cost fields hidden) and reverse them. A person who does both gets both roles ticked.
6. **Any negative adjustment counts as a write-off and needs an Admin**, MP wastage included.
7. **One day end per date for the whole shop, closed only by itself.** The day opens on the first bill on any PC and closes when the shop is next used on a later date (the dashboard counts those). There is no cash count (no cash drawer) and no counter (every PC is the same).
8. **Cash rounding** setting: none by default; Rs 1, 5 or 10 are possible, stored as a rounding adjustment on the bill.
9. **Reprints** are numbered from #2; the original print is copy #1.
10. **PINs are stored as HMAC-SHA256** with the server's `PIN_SECRET`, so a PIN alone can identify the user (they are unique). Losing `PIN_SECRET` means resetting every PIN.
11. **Reusing a sub-product** updates its actual price to the weighted average of stock on hand. Free items can change the actual price even when the cost matches.
12. **Customers** have no table. Names and phones are stored on the bill, and suggestions come from earlier bills.
13. **The billing lookup sends `maxDiscount`** (purchase discount, capped so the price stays at or above cost) instead of cost, so the screen can enforce limits without revealing cost.
14. **Boxed items:** Value, Qty, Free and the purchase discount are per box. R-price, W-price, the sales discount and the sales price are per piece.
15. **Old bills follow product renames** (the owner asked for this). It overrides the plan's "old bills never change" for names and codes only: prices, quantities and totals stay as sold. A bill line keeps its text if someone had changed it separately; only lines still showing the old text are updated.
16. **Permission changes for one user** are stored as differences from their roles: "add X" or "take away Y". If the roles change later, the differences still apply. A Super Admin always has everything, and Super Admin-only permissions can never be given to anyone else.
17. **Customised built-in roles** keep their name. The Super Admin role can't be edited.
18. **Test mode is per user and works on a full copy** (the owner asked for single accounts, switched by the Super Admin who is usually away), rather than flags on rows, so nothing in test mode can leak into real figures. Against misuse: only the Super Admin switches it, the user's screens show it, every slip says TEST, the drawer stays shut, and each switch with the test bill count is kept in the real audit log. It has no time limit (the owner's call), so a user left in test mode keeps their sales out of the real data until someone notices the red frame.
19. **The online panel is for looking; only the Super Admin changes things there, and only what an Admin can't** (the owner's rules). It serves several shops, each in its own copy database, with a sign-in per shop (users are each shop's own). An online change is a set of row changes the shop applies when it connects, checked field by field: no conflict when different fields changed, a Super Admin decision when the same field changed at both ends. Stock and money only change at the shops.
20. **Updates come from GitHub Releases of this (public) repository**, checked with SHA-256 over HTTPS, not with a separate signing key: a key kept in GitHub's secrets would be usable by anyone who controls the repository anyway. Authenticode signing of the installer is the next step when a certificate is bought.
21. **PostgreSQL runs on port 5544 and only for this PC** (not 5432), so it never clashes with another PostgreSQL and no other PC can reach the database; the other PCs only talk to the server on port 3000.
22. **One installer for install and update.** The updater runs the same exe silently; there is no separate patch format, so every update is a full, tested install path with backup and rollback.

## Known gaps and rough edges

- **Fixed in 1.0.2:** in 1.0.1 a shop linked in the first-run wizard never synced until its server restarted: the installer starts the server before setup, the sync agent read the empty `cloud` setting into the settings cache, and setup didn't clear it, so the owner's account never arrived. Setup now clears the cache and syncs at once (`modules/setup/routes.ts`); the sync test runs a round before setup to cover it. A 1.0.1 shop stuck waiting needs one restart of the **Aruna POS Server** service (or the PC).
- The online panel's address for shops is `https://arunapaint.vercel.app`. The per-deployment `*-king-upes-projects.vercel.app` addresses sit behind Vercel's login (Deployment Protection), so a shop linked to one never reaches the panel.
- **Since 1.0.3, a shop waiting for the owner's account** (linked at setup, no user yet) locks the sign-in boxes until the account arrives, polls every 3 s and shows how the link is doing (`GET /api/setup/status` → `link`: host, online, last error; never the key): connecting, connected, or why it can't connect. A non-JSON answer is named in plain words (a Vercel sign-in page means "not the panel's public address"). **Change the online panel link** fixes a wrong address or key there (`POST /api/setup/cloud`, allowed only while no user exists, like the first-run wizard; logged as `setup.cloud_link`). The server also refuses sign-in in that state with "The owner's account hasn't arrived from the online panel yet" instead of "wrong password".

- **The installer passes its tests on GitHub's clean Windows machine** (run 42293146862: install, first-run setup, update with backup, updater task, uninstall keeping data, reinstall over kept data), **but has not run on the shop's own Windows 10/11 PC yet.** The rollback after a failed update is written but not exercised by CI. Printing through a shared Windows printer from the server service (running as SYSTEM) is untested.
- WinSW stops the server by ending the process rather than a graceful shutdown; bills are single transactions, so nothing half-written stays, but a request in flight at that moment fails.
- The first published release must be `v1.0.1` or later: the tag `v1.0.0` already exists on an older commit.
- The installer isn't code-signed: Windows SmartScreen asks "More info → Run anyway" the first time.
- A shop that already had PINs when it was linked to the online panel keeps its own PIN secret, so PINs set online don't work there (Cloud sync says so). New shops take the panel's secret by themselves.
- A PostgreSQL major-version change (16 → 17) is not done by the updater (it keeps the current PostgreSQL and says so in the log); that would need `pg_upgrade`.

- Cloud sync: a settings group (receipt, billing…) is one field for conflicts, so two changes to the same group at both ends always ask the Super Admin. Sent rows stay in each shop's `sync_outbox` (prune old sent rows one day). Hosting is Vercel + Neon (`docs/CLOUD_ON_VERCEL.md`); the same app also runs as a plain Node server anywhere with PostgreSQL. All shops and the cloud must share one `PIN_SECRET` for PINs set online to work.
- No reports, PDF or Excel exports yet (the dashboard has charts, see Admin below).
- No screens yet for monthly closing, commission, reorder, purchase returns, stock count, location transfers or adjustments. The shared formulas exist for closing and reorder, and the database tables exist for all of them.
- Alerts: only backup failures create alerts. Low stock shows on the dashboard straight from the stock query. Near expiry, cheques due, day end not done and high returns are not generated.
- The clock guard compares the PC with the shop server, not with the cloud.
- Native date inputs follow the browser language (they may show MM/DD/YYYY). Everything else shows DD/MM/YYYY.
- The web bundle is about 740 kB in one chunk (fine on a LAN; it could be split).
- ESLint is not set up; Prettier and `tsc` are the checks.
- The owner's own Windows dev helpers (WSL PostgreSQL bridge, `run.bat`, `push.bat`, the dummy-data script) live in `tools/dev/` (see its README); they are not part of the app or the installer.
- `e2e/start-server.sh` lost its executable bit in a commit made on Windows. It was restored in this session with `git update-index --chmod=+x`.
- No desktop shell yet (Tauri or Electron full-screen wrapper that starts with Windows and blocks browser keys).
- Test mode needs the database role to have CREATEDB (the message says so if it is missing); it doesn't need `pg_dump`. Backups do: `core/pgtools.ts` finds `pg_dump` in `PG_BIN_DIR`, then PATH, then PostgreSQL's usual install folders (`C:\Program Files\PostgreSQL\<version>\bin` on Windows, which the installer doesn't add to PATH), and says which folder to set when it is missing. The copy (`<db>_testmode`) stays on disk until it is refreshed. The sync agent reads only the real database (`testMode.production`), never the copy. A new in-memory cache of database rows must be kept per scope (see `SettingsService`) or reset in `TestModeService`'s `onChange`.

## How the API is organised

All routes are under `/api`. Each module has `routes.ts` (HTTP, permission guards, transactions) and `service.ts` (rules) under `apps/server/src/modules/<name>/`:

- **Auth and setup:** `setup/` (first run), `auth/routes.ts` (login, logout, me, PIN switch/unlock, lock, change password, recover, shortcuts, verify-approval).
- **Admin:** `users/` (users, roles, sessions), `admin/` (settings, number formats, audit log), `values/` (value manager), `system/` (status bar, alerts, backups, test mode, the `/api/live` WebSocket).
- **Stock:** `suppliers/` (suppliers, ledger, payments, cheques), `products/` (products, search, sub-products, prices, bin card), `purchases/` (GRN), `mixpaint/`, `stock/` (transfers, adjustments, stock per location).
- **Billing:** `sales/` (lookup, status, sales, hold, history, void, reprint, convert, returns, receipt printing), `shifts/` (day end).

The integration tests in `apps/server/test/*.test.ts` double as executable examples of every flow (see `fixtures.ts` for building a catalog and posting GRNs).
